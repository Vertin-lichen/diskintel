# 数据口径说明：空间页的数字到底是真实还是虚假（2026-11-13）

> 起因：机主发现空间页 C 盘显示「已用 320.8 GB / 容量 299.1 GB = 100%」，与资源管理器不符。
> 结论先说：**数字来自真实快照，但不是「卷占用」，而是「文件逻辑大小之和」**。
> 这两者在 NTFS 上天然不相等，界面上把它们当成同一件事，是产品缺陷。

## 1. 两类数据，两种来源

| 界面元素 | 数据来源 | 是否实时 |
|---|---|---|
| 容量、剩余空间、实际已用 | Win32 `GetDiskFreeSpaceExW`（每次打开空间页刷新） | ✅ 实时 |
| 已用（旧实现）、目录树图、层级列表 | 快照 SQLite 里 `entries.size` 的求和 | ❌ 快照时刻（2026-11-12 10:01） |
| 检索结果、对比视图 | 快照（或 goz 实时引擎，取决于「来源」选择） | 视来源而定 |

## 2. C 盘 320.8 GB 的构成（实测）

快照 `20261112-100008`，C 盘 1,891,728 个文件：

| 分组 | 逻辑大小 | 文件数 |
|---|---:|---:|
| C:\Users | 216.6 GiB | 1,512,158 |
| C:\Windows（含 WinSxS 26.3 GiB / System32 14.9 GiB） | 51.8 GiB | 237,049 |
| C:\Program Files + (x86) | 30.4 GiB | 94,245 |
| C:\ProgramData | 16.9 GiB | 12,192 |
| NTFS 元数据（$MFT、$Extend、$LogFile…） | 4.5 GiB | 35,632 |
| 回收站 / 卷影信息 | 0.7 GiB | 35,580 |
| **合计** | **320.8 GiB** | 1,891,728 |

同一天的卷真实状态：容量 299.1 GiB、空闲 10.4 GiB → **实际已用 288.7 GiB**。
逻辑和比实际多 **32.1 GiB**，原因按贡献排序：

1. **硬链接重复计数**（最大项）：WinSxS 里 26.3 GiB 的文件绝大多数是 System32/Program Files 的硬链接，
   同一个数据块在快照里有多个路径，求和时被算了两遍；
2. **NTFS 元数据**：`C:\$MFT`（2.1 GiB）等被当作普通文件计入（4.5 GiB）；
3. **压缩 / 稀疏文件**：Chrome 权重、Android 镜像、qocw2 等逻辑大小远大于实际占用；
4. **无法识别的重解析点**：快照建库器不保存 Windows 属性位（实测目录恒 16、文件恒 0），
   因此无法在查询时剔除 junction 与符号链接。

## 3. 为什么不能简单「减去硬链接」

- 硬链接在 EFU / 快照里没有文件 ID（FileReferenceNumber），无法判断两条路径是否指向同一数据；
- 若要精确去重，建库器需要额外采集 `nFileIndexHigh/Low` 或 USN 的 FileReferenceNumber（改造点在采集端，不在 UI）；
- 因此本期采取**诚实展示**：环形图用实时占用，逻辑大小单列并解释差额。

## 4. 改进后空间页的展示口径

- 主环形图：`实际已用 = 容量 − 实时空闲`（与资源管理器一致）；
- 副行：`快照逻辑 320.8 GiB（含硬链接与系统文件，比实际多 32.1 GiB）`；
- 逻辑 > 容量时不再显示 100% / 超出容量，改为在脚注说明差异原因；
- 树图与层级列表仍按逻辑大小（用于比较目录之间的相对大小），页面底部注明「面积按逻辑大小，硬链接可能重复计入」。

## 5. 「卷九 9dba3ee0」是什么

`\\?\Volume{9dba3ee0-5ad5-4126-81f9-40064982c00e}\` 是磁盘 0 第 4 分区：
**Recovery（恢复分区），907 MB，无盘符**。旧实现把所有快照根都画成卷卡片，于是它显示成一个没头没脑的「卷九」。
改进后它归入「系统保留（无盘符）」折叠区，并标注为「恢复分区」。

## 7. 一句话回答「数据真实还是虚假」

**真实，但口径不同**：检索与空间视图读的是快照（某一时刻的真实文件列表）；
容量/空闲是实时 API；两者混用且不标注差异，才会显得「C 盘 320 G 比盘还大」。
本期把两类数据分开呈现，并在界面上写明来源与时间。
