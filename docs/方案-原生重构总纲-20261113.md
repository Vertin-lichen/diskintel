## 0. 一页结论

现有三份资产各有所长，也各有硬伤：

| 资产 | 长板 | 硬伤 |
|---|---|---|
| `磁盘情报系统`（Python + Web 六视图） | 功能最全：检索/树图/对比/快照管理/证据/设置、445 项测试、MCP、双引擎编排 | WebView2 静态成本 ~1 GB RSS、17 个进程；建库 85 s、单快照 1.5 GB |
| `diskintel-rs`（egui 原型 0.2.0） | 纯原生、83 MB RSS、4.2 ms/帧、开窗口 0.3 s | UI 是 egui 默认皮肤，信息架构与 Web 版脱节；三视图残缺；无 AI 接口 |
| `goz`（MIT，MFT+USN 引擎） | 毫秒级索引、Everything 兼容查询、已在本机提权运行 | 只是引擎，无持久化快照、无 UI |

**重构目标：把三者合成一个产品**——一个纯原生、单进程、< 100 MB 常驻、UI 达到甚至超过 Web 观感、
检索对标 Everything、空间可视化对标 WizTree、快照对比对标 WhoShitsOnMyC 的软件，
同时天然对 agent 友好（MCP + `--json`），并把快照存储从"每份全量"改成"基线 + 增量链"。

一句话：**渲染换原生、存储换增量、引擎双档、接口双通道（人/AI）。**

## 1. 现状诊断（为什么现在的原生版"和 Web 毫无关系"）

把两份截图放在一起看，问题不在"egui 画不出好看的界面"，而在四件事：

1. **没有设计系统。** 原型的颜色、间距、边框、悬停态全部是 egui 默认值；
   类型区分靠 20 px 宽的灰色圆角色块 + 中文字（"盘/夹/?"），在 4.46M 行里既占宽又难扫读。
2. **信息架构错位。** Web 版是「菜单栏 → 视图标签 → 检索条件栏 → 表头 → 行 → 状态栏」六层结构，
   原型只剩「输入框 + 下拉 + 表头 + 行」。列缺失（大小/时间/类型没显示）、无条件过滤条、
   无分页/加载更多、无排序指示、无右键菜单、无空态、无快捷键。
3. **图标体系缺失。** Web 版每种类型是一枚 16×16 的**彩色矢量图标**（11 类），
   原型退化成中性色块——这是"美观度"差异的最大来源，也是扫读效率的关键。
4. **数据维度的浪费。** 原生版读的是同一份 SQLite，但只用了 `path/name/size/mtime/is_dir`，
   Web 版已经把目录聚合（`folder_sizes`）、差异、存储水位、证据都用上了。

结论：**不是换框架能解决的问题，是缺一套设计系统 + 一次信息架构重排。** 这也是本次重构的主线。

## 2. 产品形态：一个进程，三条主线，两种用户

```
┌─ 磁盘情报系统.exe（唯一常驻进程，纯原生 GPU 直绘）────────────────────┐
│  UI 层      egui 0.37 / glow：菜单栏 · 视图标签 · 条件栏 · 表/图 · 状态栏      │
│  ────────────────────────────────────────────────────────────────  │
│  业务层     检索（语法解析/排序/分页）· 空间（聚合/树图布局/饼图）· 对比（归并） │
│  ────────────────────────────────────────────────────────────────  │
│  数据层     ① 内存引擎 goz（MFT+USN 实时索引，毫秒级，需提权守护）             │
│            ② 存储引擎 快照库（SQLite v4：全量基线 + 增量链 + 冷压缩）           │
│  ────────────────────────────────────────────────────────────────  │
│  接口层     人：窗口 ｜ AI：MCP stdio ｜ 脚本：--json 动词（与窗口同口径）      │
└──────────────────────────────────────────────────────────────────┘
外部依赖：goz.exe/gozd.exe（可缺省，缺省时自动落到存储引擎）
```

设计原则（按优先级）：

1. **人机同源**：窗口里每个动作都对应一条 `--json` 动词，状态栏实时显示该命令；AI 与人不走两套逻辑。
2. **引擎可换，数据模型自有**（own the data model, rent the engine）：GoZ 只是"快"的来源，
   快照是"证据"的来源；任何一方缺失都不影响启动。
3. **空间换内存**是对的，但要可预算：内存引擎把索引压进 RAM（快），存储引擎用磁盘换内存（稳）；
   用户/软件按档位自选，绝不把选择权埋在代码里。
4. **零常驻依赖**：不装服务、不写注册表、不常驻第三方进程；gozd 由机主一次性授权，平时可不在。

## 3. 原生 UI：设计系统先行

### 3.1 为什么仍是 egui（而不是 Tauri / iced / Slint）

| 方案 | 结论 |
|---|---|
| Tauri / WebView2 | 已实测静态基线 1 GB RSS、17 进程；与"降内存"目标直接冲突，否决 |
| iced | 保留态架构、文本布局好，但自绘树图/饼图要绕 Canvas，且生态与字体美化成本高 |
| Slint | 声明式好看，但 CJK 与自绘能力受限、许可与打包约束 |
| **egui（采用）** | 即时模式 = 每帧只画可见行，天然虚拟化；Painter 可画任意矢量（图标/树图/饼图）；单 exe、GPU 直绘、4 ms/帧已验证 |

关键认知：**egui 的"原生感"取决于我们交给它的设计令牌与自绘组件，而不是它本身。**
默认皮肤丑，是因为没人做设计系统。本次把 Web 版的观感翻译成 egui 的设计令牌 + 自绘控件。

### 3.2 设计令牌（Design Tokens）

- **色彩**：深色/浅色双主题；中性灰阶 7 档 + 品牌蓝 `#2563EB`（accent）+ 语义色（成功/警告/危险）。
  行选中/悬停用 accent 的 8%/12% 透明度；分隔线 1 px `#E5E7EB`（浅）/ `#2A2F3A`（深）。
- **间距**：4 px 基准，常用 4/8/12/16/24；表格行高 28 px、工具栏 40 px、菜单栏 32 px、状态栏 26 px。
- **圆角**：控件 6 px、卡片 10 px、胶囊 999 px；描边 1 px，无重阴影（仅浮层 8 px 柔光）。
- **字体**：Segoe UI（拉丁）+ 微软雅黑 UI（CJK）+ Consolas（路径/数字，等宽对齐）；
  13 px 正文、11 px 辅助、15 px 标题；数字右对齐并用 tabular 数字宽度。
- **图标**：16×16 矢量，11 类文件类型带专属色，UI 动作图标（搜索/刷新/齿轮/折叠/复制/打开）同构同线宽（1.5 px 圆头）。
- **动效**：仅三处——悬停高亮 90 ms、视图切换 120 ms 淡入、下钻 160 ms 缓动；其余不动，避免干扰扫读。

### 3.3 布局骨架（三个核心视图共用外壳）

```
┌ 菜单栏 32px ─────────────────────────────────────────────┐
│ 磁盘情报系统   文件  视图  工具  帮助          引擎● 扫描 │
├ 工具栏 40px ─────────────────────────────────────────────┤
│ [检索][空间][对比][快照]   │ 🔍 搜索框(含语法提示) │ 快照▾ │
├ 条件栏 32px（仅检索/对比）─────────────────────────────────┤
│ 来源▾ 类型▾ 排序▾ 扩展名 大小范围 路径范围  [应用] [重置]    │
├ 内容区 ───────────────────────────────────────────────────┤
│  …表格 / 树图 / 差异列表…                                  │
├ 状态栏 26px ──────────────────────────────────────────────┤
│ 对象 4,461,929 · 1.47 TB │ 命中 1,204 · 8 ms │ 快照 … │ RSS │
└───────────────────────────────────────────────────────────┘
```

- 表格：虚拟滚动（只查可见 ± 1 屏）、列宽可拖、表头点击排序、行斑马、悬停/选中/焦点三态、
  右键菜单、双击打开、`Ctrl+C` 复制路径、`↑↓` 移动、`Enter` 打开。
- 空间视图：上=物理磁盘卡片（每盘一张：型号/容量/分区饼图/空闲扇区/图例），
  下=左侧 55% 矩形树图（面积=字节，色=类型/深度，悬停浮层，点击下钻），右侧 45% 父子层级列表。
- 对比视图：左=快照时间线（A/B 选择），右=四类差异（新增/消失/增长/缩小）分组列表 + 汇总条。

## 4. 检索：对标 Everything 的语法与速度

- 语法：空格 AND、`!` 排除、`|` 或、引号短语、通配 `*` `?`、正则 `/…/`；
  过滤器 `ext:` `size:>10m` `after:2026-01-01` `before:` `kind:file|dir` `path:` `dm:`（修改日）；
  排序 `sort:size|date|path|name`，默认"智能排序"（文档优先、系统/缓存降权）。
- 交互：260 ms 防抖 + 回车立即；结果分页/加载更多；来源徽章（实时/快照）；
  命中数、耗时、当前等价命令实时显示。
- 对齐 Everything 的部分：即时性、列可配、正则、大小/日期过滤、`!` 排除、右键动作、状态栏统计。
- 超越 Everything 的部分：类型矢量图标与色标、低价值结果降权、快照对比下钻、原生树图、AI 动词。

## 5. 快照：从"每份全量"到"基线 + 增量链"

### 5.1 问题

现状 5 份全量快照 ≈ 9.5 GB，单份 1.5 GB / 446 万行 ≈ 336 B/行；按日快照一年就是数百 GB。
而两份相邻快照的差异通常只有 1%~5%。**全量重复存储是主要浪费。**

### 5.2 方案（v4）

1. **字典化**：`names`（basename 字典）与 `dirs`（目录 id 表）拆开，条目只存
   `parent_id + name_id + size + mtime + attrs`，改造后单份全量预期 `[待回填]`。
2. **增量链**：`base`（周期全量）+ `delta`（相对前一版的 added/removed/changed，change-log 排序）。
   读任意版本 = base 与 delta 流式归并（O(n)，不落盘）；写新快照 = 只写 delta。
3. **重基**：每 K 份（默认 5）或 delta 合计 > base/4 时重基，链条长度有上界，读路径可预测。
4. **冷压缩**：超过热窗口的快照整库 zstd，空闲时后台压缩；`[待回填]`压缩比实测。
5. **GC**：按保留策略（份数/总量/水位）淘汰，先删最老 delta 再删 base；淘汰只移入 `待删除/`。
6. **兼容**：v3 只读兼容 + 一次性导入迁移；`meta.format_version` 显式版本化，禁止静默猜测。

预期收益（待实测回填）：5 份 ≈ 9.5 GB → 约 `[待回填]`，长期保留成本下降一个量级。

## 6. 双引擎：内存优先 / 存储优先 / 自动

| 档位 | 数据源 | 延迟 | 常驻成本 | 适用 |
|---|---|---|---|---|
| `memory`（内存优先） | goz 实时索引（MFT+USN，RAM） | 毫秒级 | +gozd 内存（可配上限） | 强交互、频繁检索 |
| `storage`（存储优先） | SQLite v4 快照 | 数十~数百 ms | ~50–100 MB | 低内存机器、离线取证 |
| `auto`（默认） | 有 gozd → memory；否则 storage；快照过期时后台补 | 自适应 | 自适应 | 绝大多数用户 |

规则：搜索结果的 `engine_source` 必须如实标注；引擎切换不改变结果口径（同一套排序/过滤在两侧同义实现）；
gozd 不可用/未授权时**不做任何阻塞式弹窗**，状态栏降级提示 + 后台可重试。

## 7. AI 接口（人可用，AI 亦可用）

- `--json <verb>`：`status/snapshots/search/du/top/diff/sql/diff-tree/snapshot-*/engine-*`，与窗口同口径。
- `mcp`：stdio JSON-RPC 2.0，暴露 9 个只读工具（沿用 Python 版工具名，保证既有 agent 配置不失效）。
- 结构化错误：`{"ok":false,"error":{"code","message","hint"}}`；退出码沿用 Python 版约定。
- 每个 UI 动作都在状态栏显示其等价命令，方便人工抄给 agent 复现。

## 10. 实测回填（2026-11-13 凌晨，全部在本机实测）

### 10.1 原生窗口

| 指标 | 目标 | 实测 |
|---|---|---|
| 冷启动到首帧 | ≤ 400 ms | **253–498 ms**（窗口创建占 ~240 ms，字体 +6 ms，快照列表 +4 ms） |
| 常驻 RSS | ≤ 120 MB | **100–125 MB**（检索大结果集时峰值 ~250 MB，因全表扫描页驻留） |
| 进程数 | 1 | **1**（建库/索引时临时 2） |
| 检索延迟（快照引擎，全表关键词） | ≤ 250 ms | **8–350 ms**（取决于命中量；134k 命中约 10–300 ms） |
| 检索延迟（实时引擎） | — | **7–15 ms**（goz 常驻管道，134k 命中） |
| 空间视图目录加载 | ≤ 16 ms | **6–11 ms**（WinSxS 3 万子目录 15–26 ms） |
| 对比两份 446 万行快照 | — | **3.4 s**（游标归并快路）/ 20–25 s（分步 SQL 兜底） |

### 10.2 快照存储（研究报告实测，代码已落地）

| 方案 | 单份体积 | 说明 |
|---|---:|---|
| v3（现状） | 1503 MiB | path 与 parent_path 各写一遍，占 79.9% |
| v3-slim（去 parent_path） | 975 MiB | 只省 1.5× |
| **v4 字典化（已实现）** | **289.9 MiB** | **5.18× 压缩**，13.6 s/份，校验行数/字节/rollup/integrity 全通过 |
| v4 + delta 链（设计完成） | 5 份约 190 MiB | 51×，需重基周期 K=8 与链校验 |
| 冷快照 zstd-3 归档 | 原体积 5.9% | 1.5 GiB → 约 88 MiB（第二期） |

真实数据还发现：**5 份现有快照里有 3 份是完全相同的数据**（同一 EFU 的 sha256），
两两 diff 均 0 行 —— 零代码即可回收 3.35 GiB，属于「重复观测」而非历史价值。

### 10.3 双引擎（goz 常驻管道）

| 项 | 实测 |
|---|---|
| connect（含属主 SID 校验） | 0.33–0.75 ms |
| Hello / Status | 2.2–2.9 ms |
| 查询 *.exe（16,775 命中） | 7.3–7.6 ms |
| 查询 dll（134,258 命中） | 14.9 ms |
| 全盘按大小排序前 100 | 200–229 ms |
| 与 goz.exe CLI 对拍 | 命中数与前 3 行逐字段一致 |
| 降级 | 管道不存在 1.7 ms 返回原因；属主非 SYSTEM/Administrators 时 fail-closed |

**引擎能力边界（重要）**：goz 不支持 `|`（或）与 `!`（排除），
`/正则/` 会被当普通文字静默返回 0 条 —— GUI 侧已加查询守卫，拦下后回落到快照引擎并如实提示。

### 10.4 与 Web 版的对照

| | Web 版（Python + WebView2） | 原生版（本仓库 0.3.0） |
|---|---:|---:|
| 冷启动 | 3.5–5.0 s | **0.25–0.5 s** |
| 常驻内存 | ~1 GB（17 进程） | **~100–125 MB（1 进程）** |
| 检索 4.46M 行 | 30–300 ms（HTTP + SQL） | 10–350 ms（本地 SQL / 7–15 ms 实时引擎） |
| 视觉 | 浏览器排版 | **GPU 直绘 + 矢量图标，同一套设计令牌** |

### 10.5 环境陷阱（值得写进灾备手册）

沙箱会对「工作区内编译出的 exe」附加写限制（工作区外路径拒绝写入）。
复现方式：把 exe 复制到工作区外运行即可。本仓库的 `--shot` 截图自检因此要求 exe 在工作区外执行。
