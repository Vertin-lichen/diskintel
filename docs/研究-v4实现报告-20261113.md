## 3. 查询实测（v3 vs v4，同进程同快照，各 3 次取中位，热缓存）

| 查询 | v3 (ms) | v4 (ms) | 结论 |
|---|---:|---:|---|
| count("dll") | 1096.67 | 468.25 | v4 快 2.34× |
| page("dll", 路径排序, 0, 200) | 7.23 | 833.87 | v4 慢 115× |
| child_dirs("C:\Windows", 100) | 0.19 | 0.20 | 持平 |
| child_files("C:\Windows", 100) | 413.06 | 0.14 | v4 快 2950× |
| dir_info("C:\Windows") | 0.11 | 0.10 | 持平 |

- 结果一致性：page / child_dirs / child_files / roots 的路径+大小指纹逐条相同；count 全部相同（见第 4 节）。

## 5. 实现要点（按规范逐条）

1. 建库 PRAGMA：page_size=8192（读回断言，VACUUM 后再断言）、journal_mode=OFF、synchronous=OFF、temp_store=MEMORY、locking_mode=EXCLUSIVE、cache_size=-262144。
2. 表：meta / names / dirs / entries / rollup / dir_paths 全部 WITHOUT ROWID，主键与规范一致；索引 idx_rollup_size、idx_entries_name、idx_dirs_parent（最后一个是子目录枚举必需，7.2 MB）。
3. id 规则：names 按全库频次降序（同频按名字升序，保证可复现）；dirs 按 path 字典序 1..N；卷根 name 存整条前缀（C:\、\\?\Volume{...}\），parent_id=-1；目录不入 entries。
4. 写入顺序：names 按 id、dirs 按 id、dir_paths 按 id、entries 按 (parent_id,name_id) 升序（先内存排序再顺序追加，B 树顺序写）。
5. meta 键：format_version=4、layout=dict-v4、row_count、file_count、dir_count、name_count、total_size、chain_depth=0、converted_at、converter，并继承 v3 全部键（created_at、engine、generator_version、source_efu、volume_roots、excluded_*、decode_* 等）。verify_sha256 未写（规范标注可选），改用运行时校验 + integrity_check。
6. 读侧检索：没有 entries.path，所以 count/page 的条件全部先落到 names.name / dir_paths.path 的 IN 子查询，再按 id 取行；SQLite 选 MULTI-INDEX OR（idx_entries_name + entries 主键），不碰 1.5 GB 路径文本。
7. 跨分隔符命中：拼路径时中间会插一个分隔符，所以条件里带 \ 或 / 时按分隔符位置枚举拆分（父路径后缀 + 名字前缀），与 v3 的 path LIKE 等价（Windows\explorer 实测 52=52）。
8. 路径回填：查询时用 p.path || CASE 父路径末尾是否分隔符 THEN '' ELSE '\' END || n.name；child_files 用已知父路径 + join_path 在 Rust 侧拼，省掉一次 join。
9. 只读层：READ_ONLY + NO_MUTEX、query_only=ON、mmap 256 MiB、cache 64 MiB、temp_store=MEMORY；format_version != 4 直接报错。
10. 目录 id 查找：dirs id 按 path 字典序分配 ⇒ dir_paths 天然按 path 有序，直接在 dir_id 上二分（约 20 次主键查），不给 90 MB 的 path 列再建索引；查不到再退回一次线性查（兼容将来 delta 追尾）。

## 6. 遗留风险与建议

1. **路径序分页退化（最大风险）**：v4 没有路径索引，page(path 排序) 必须把命中集整体拼路径 + 排序，833.87 ms vs v3 的 7.23 ms；且每次翻页都会重排。建议 GUI 侧对同一条件缓存排序结果，或默认加 scope/按大小排序。按 id 顺序（即目录序）出页是后续可做的优化，但需要额外的「目录内按名字序」索引。
2. **时间条件语义变化**：v4 按 Unix 秒正确比较，v3 恒为 0；dirs 表没有 mtime，所以带 after/before 的条件只作用在文件行。改行为前需 Lead 确认要不要保持 v3 的「坏语义」。
3. **ext 由名字推导**：v3 建库器把 ext 截断到 32 字符（实测 460 行，占 0.012%），这类超长扩展名在 v4 里按完整后缀匹配，行为略有不同。
4. **names/dirs 的 id 只对 base 成立**：将来做 delta 链必须「只追加不重排」；当前 meta.chain_depth=0，没有 delta 支持。
5. **dir_id 二分依赖 id 连续且按路径序**：非法情况有线性兜底，但慢（约 40 ms/次）。
6. **转换内存 1.36 GB**：32 GB 机器没问题；若要压到 500 MB 以内，可把 temp_store 改 FILE、写缓存降到 64 MB（代价是转换慢一些）。
7. **21 行路径含 U+FFFD**：v3 里就是这样（decode_replaced 却是 0，属旧口径问题），本次原样继承。
8. **page 的 NameAsc/NameDesc 仍按路径近似**（与 v3 相同），不是真名字序。
9. **输出覆盖**：目标文件已存在时直接 rename 覆盖（原子），不删旧文件、不做备份。
10. **未实现**：delta 链、重基、migrate 命令、VACUUM INTO、verify_sha256、4 KiB/16 KiB 页对比。
